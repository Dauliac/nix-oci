# dependency-updates spec

## ADDED Requirements

### Requirement: Per-input update PRs

The dependency update automation SHALL open one pull request per Nix
flake input on every scheduled sweep, so that a broken upstream bump
can be closed in isolation without blocking other inputs.

#### Scenario: Two independent inputs move upstream

- **WHEN** upstream `nix2container` and `flake-parts` both publish new
  commits since the last sweep
- **THEN** the automation opens two separate pull requests, one per
  input, each modifying only the corresponding entry in `flake.lock`

#### Scenario: One PR fails CI, another is unaffected

- **GIVEN** two open bot PRs, one bumping `nix2container` (CI red) and
  one bumping `flake-parts` (CI green)
- **WHEN** a maintainer closes the `nix2container` PR without merging
- **THEN** the `flake-parts` PR remains open and eligible for merge

### Requirement: nixpkgs channel pinning

The automation SHALL restrict `nixpkgs` updates to commits reachable
from the currently pinned channel branch (`nixos-25.11`). Cross-channel
migrations (for example `nixos-25.11 -> nixos-26.05`) SHALL NOT be attempted
by the automation.

#### Scenario: Channel-internal update

- **WHEN** the `nixos-25.11` branch of nixpkgs moves forward
- **THEN** the automation opens a PR bumping the `nixpkgs` rev to the
  new tip of `nixos-25.11`

#### Scenario: New nixpkgs channel released

- **WHEN** a new nixpkgs channel `nixos-26.05` is released
- **THEN** the automation does NOT open a PR migrating to it

### Requirement: Automerge gate

The automation SHALL automerge a pull request only when ALL of the
following hold:

1. The update type is `patch` or `minor` (never `major`).
2. All GitHub branch-protection required status checks pass.
3. The dependency isn't `nixpkgs`.
4. The PR doesn't carry a `security` label.

Any PR failing any of the four conditions requires human merge.

#### Scenario: Green patch bump of a non-nixpkgs input

- **GIVEN** a bot PR bumping `flake-parts` from `1.2.3` to `1.2.4`
  with all required checks green
- **THEN** the PR is automerged without human intervention

#### Scenario: Major bump on a non-nixpkgs input

- **GIVEN** a bot PR bumping `import-tree` from `1.x` to `2.x` with all
  required checks green
- **THEN** the PR is NOT automerged and remains open for review

#### Scenario: Patch bump of nixpkgs

- **GIVEN** a bot PR bumping `nixpkgs` to a new tip of `nixos-25.11`
  with all required checks green
- **THEN** the PR is NOT automerged and remains open for review

### Requirement: Nix-authored workflows

All GitHub Actions workflows introduced by this capability SHALL be
declared under `githubActions.workflows.<name>` in the docs partition
of the flake, so that they're generated by the existing
`docs-github-workflows` derivation. Hand-written YAML under
`.github/workflows/` for these workflows is prohibited.

#### Scenario: Adding the config validator workflow

- **WHEN** a maintainer adds a Renovate config validator workflow
- **THEN** the workflow is declared as
  `githubActions.workflows.renovate-config-validator` in `nix/docs.nix`
- **AND** the corresponding YAML at
  `.github/workflows/renovate-config-validator.yml` is a byte-for-byte
  copy of the output of `nix build .#legacyPackages.x86_64-linux.docs-github-workflows`

#### Scenario: Adding the fallback lock updater

- **WHEN** a maintainer adds an `update-flake-lock` fallback workflow
- **THEN** it's declared as
  `githubActions.workflows.update-flake-lock` in `nix/docs.nix`
- **AND** the committed YAML matches the generated output

### Requirement: Config validation on every relevant PR

The automation configuration file (`renovate.json5`) SHALL be validated
by CI on every pull request that touches it, so that syntactic
regressions can't land on `main`.

#### Scenario: PR modifies renovate.json5

- **WHEN** a PR modifies `renovate.json5`
- **THEN** the `Renovate config validator` workflow runs
- **AND** the PR can't be merged if validation fails

#### Scenario: PR doesn't touch renovate.json5

- **WHEN** a PR modifies only source files unrelated to
  `renovate.json5` or the validator workflow
- **THEN** the `Renovate config validator` workflow does NOT run
  (cost stays zero on unrelated PRs)

### Requirement: Fallback lock refresh path

The repository SHALL provide a Nix-authored GitHub Actions workflow
that refreshes `flake.lock` on a scheduled cadence and on manual
dispatch, independent of any hosted third-party bot, so that the
project remains updateable if the Renovate app is uninstalled.

#### Scenario: Renovate app is uninstalled

- **GIVEN** the Mend Renovate app isn't installed on the repository
- **WHEN** the scheduled trigger of the `update-flake-lock` workflow
  fires
- **THEN** the workflow opens a single pull request updating the
  entire `flake.lock`
- **AND** the pull request is NOT automerged (human review required)

#### Scenario: Manual dispatch

- **WHEN** a maintainer manually dispatches the `update-flake-lock`
  workflow
- **THEN** the workflow runs and opens a pull request following the
  same behavior as the scheduled trigger
