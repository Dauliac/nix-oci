## Why

`mkAutoLabels` accepts a `dependencies` list but only emits its
cardinality as `io.github.dauliac.nix-oci.nix.dependency-count`. Every
element in that list is a normal Nix derivation carrying `pname`,
`version`, `meta.description`, `meta.license` and `meta.homepage`, and
those fields are already destructured for the main `package`. The
information is there; we throw it away.

At the same time the `docs/content/architecture/automatic-labeling.md`
page has drifted from the actual label output: it lists most groups but
never fully enumerates them (for example, the `nix.deps` gap once we
add it, and the existing `provenance.*` group is documented under
"Nixpkgs security" without a heading of its own).

## What Changes

- `mkAutoLabels` in `nix/lib/oci.nix` gains one new label,
  `io.github.dauliac.nix-oci.nix.deps`, a JSON string encoding a list of
  `{ pname, version, description }` objects, one per element of the
  `dependencies` argument. The label is omitted when `dependencies` is
  empty. Ordering is preserved from the input list; ordering is
  deterministic because the input is a Nix list.
- Unit tests in `nix/modules/oci/lib/mkAutoLabels.nix` gain two
  assertions: the new label is present with the expected JSON when
  `dependencies` is non-empty, and it is absent when `dependencies` is
  empty.
- `docs/content/architecture/automatic-labeling.md` is rewritten so
  that every label `mkAutoLabels` emits appears in exactly one row of a
  table on the page, grouped by namespace. New rows for
  `nix.deps`. Section headings are added for the `provenance.*` group
  and the `security.insecure` boolean, which today are described in
  prose without appearing in any table. A "Complete label matrix"
  reference table at the top of the page cross-links every label to its
  section.
- No change to public option surface: `oci.autoLabels`, `oci.labels`,
  and the merge order are unchanged.

## Capabilities

### New Capabilities
- `auto-labels`: Deterministic OCI labels autogenerated from container
  configuration, covering OCI standard annotations, build metadata,
  runtime info, hardening posture, Kubernetes PSS/SecurityContext
  hints, network hints, Nix package identity (including main
  dependencies), and nixpkgs security metadata.

## Impact

- **Code**: `nix/lib/oci.nix` (function body of `mkAutoLabels`, adds
  ~15 lines around the `nixIdentity` attrset).
- **Tests**: `nix/modules/oci/lib/mkAutoLabels.nix` (adds two
  assertions to the existing test cases; no new test entrypoint).
- **Docs**: `docs/content/architecture/automatic-labeling.md`
  rewritten in place. `docs/content/architecture/container-metadata-wiring.md`
  gains a one-line reference to the new `nix.deps` label so the two
  pages stay consistent.
- **Callers**: no signature change. Both existing callers
  (`nix/modules/oci/lib/mkOCIImage.nix:54` and
  `nix/modules/deploy/nix-oci/options/_containers/image.nix:65`)
  already pass `dependencies = oci.dependencies`, so the new label
  materialises automatically.
- **Registries and manifest size**: one additional label per image.
  With typical `oci.dependencies` lists (0 to 20 elements) the JSON
  payload stays well under the 4KB per-label soft ceiling that Docker
  Hub and GHCR enforce. A guard in the design document caps the JSON
  at 4096 bytes; overflow truncates the list rather than the string.
- **SBOM overlap**: this label is a summary of the user-declared
  direct dependencies (the `oci.dependencies` list), not the transitive
  Nix closure. It complements the existing syft-backed SBOM pipeline
  under `nix/modules/oci/security/sbom/` and does not attempt to
  replace it.
- **Reproducibility**: preserved. No timestamps, no impure inputs;
  output is a pure function of `package.meta` and `dependencies[].meta`.
